# ADR-0009: Deliver visibility with Grafana and OpenTelemetry

- **Status:** Accepted
- **Date:** 2026-11-22

## Context

Users need to see spend and latency by tenant, endpoint and model, budget burn-down, blocked requests, anomalies with their diagnosis, and Fusebox's own health. They also need to change budgets and policies.

## Options considered

| Option | Strengths | Weaknesses |
|---|---|---|
| **Grafana + OpenTelemetry (chosen)** | Days to build, polished by default, dashboards as code, familiar to platform teams | Mostly read-only, so poor for editing budgets. Awkward for per-tenant customer-facing views |
| Custom dashboard (Blazor or React) | Fully shaped to the domain, interactive, shows full-stack skills | Weeks of work: UI, query API, auth, styling |

## Decision

- **Gateway metrics** are exported with OpenTelemetry to **Prometheus**: latency histograms, blocked and throttled counts, queue drops, Redis state, degraded-mode flag. Labels are kept few, to avoid the cardinality problem.
- **Per-tenant and per-endpoint views** read the **Postgres rollup tables** (ADR-0004) through Grafana's Postgres data source. Hundreds of endpoints times many tenants times several models is high-cardinality data, and the database is built for it.
- **Dashboards as code** live in the repository: overview, tenant and endpoint spend, budget burn-down, anomalies (a table panel showing the diagnosis), and gateway health.
- **Admin API with Swagger** manages tenants, budgets and policies. It writes to the config table and updates Redis (ADR-0002).
- A **custom UI** is a stretch goal, not part of the core plan.

## Why

- Effort goes into the gateway, which is the real differentiator.
- A reviewer can run `docker compose up` and see populated dashboards, and the screenshots make a strong README.

## How it works

- **Metrics.** The gateway counts requests (by route, outcome and status class), request duration as a histogram, refusals (by reason), money charged, a 0/1 degraded-enforcement gauge, repeated requests, which vendors are cut off and how many calls that refused, and the telemetry queue and alert deliveries. They are pushed over OpenTelemetry (OTLP/HTTP) straight into Prometheus's own OTLP receiver, so there is no scrape endpoint to expose and no collector to run. With no address set they are still counted but not sent. Tenant and model are never labels: a series is kept for every label combination, and one tenant per label would grow without limit.
- **Dashboards.** Three, loaded from files in `deploy/grafana`, so they are reviewed like code. *Overview* (traffic, latency, spend, refusals, degraded mode, queue and delivery health) reads Prometheus. *Spend & budgets* (spend by tenant, route and model, budget used in the current window, tokens per call) and *Anomalies & alerts* (each anomaly with its diagnosis, every alert, and whether each notification arrived) read the Postgres rollups. Grafana connects with a role that can only read.
- **Admin API.** Under `/admin`, with Swagger UI at `/admin/swagger`. It creates tenants, changes budgets, disables or enables a tenant, rotates keys, sets prices (now or scheduled), and lists open anomalies and alerts. A tenant's key is generated by Fusebox, shown once, and stored only as a hash. Callers send one shared admin key in `X-Admin-Key`, compared as hashes in constant time. It is off by default, and when off the routes do not exist.
- **Changes take effect without touching counters.** The admin writes to the tenants and prices tables and asks the catalog to reload. This gateway serves the change within `CatalogSource:SyncInterval` (15 seconds by default), and other instances take it from the shared Redis copy. Budget limits are read from the catalog on every call, so no spend counter is edited and nothing already spent is forgotten.
- **Every query is checked.** The dashboards are generated from one script, and each panel's query was run against live Prometheus and Postgres data. That caught a query that Grafana expanded into invalid SQL.
- **A demo that fills them.** `docker compose up --build` starts the gateway, Redis, Postgres, Prometheus and Grafana, plus a small demo app that stands in for the vendor, receives alerts, creates its tenants through the admin API, and sends steady traffic. One tenant runs away partway through, and another is too small for its traffic.

## Consequences

- Anomaly and diagnosis cards are table panels rather than rich cards. Acknowledge and dismiss actions are not available in Grafana.
- No per-customer row-level access in the dashboards.
- Metrics only, no traces. A request's path through the gateway cannot be followed in a trace viewer yet.
- The admin API has one shared key, so its audit lines say what changed but not who changed it, and failed attempts are logged but not rate limited. Run it on a private network or behind a proxy that does both.
- Routes, failure modes and other policy are still set in configuration files, not through the admin API.
- Rollup-based panels trail live traffic by a minute or two. Counters that only exist after their first event (refusals, dropped records, alert deliveries) show no data until one happens.
- The compose stack uses demo-only passwords and an anonymous read-only Grafana. It shows the system working. It is not a production deployment.
- Checked by running the stack: the demo created its tenants through the admin API, the gateway served them within seconds, one tenant's budget ran out (a critical alert, then a resolve notice), and the runaway tenant was detected at about 10 times its normal volume, diagnosed, and alerted with a trigger, a diagnosis update and an escalation, all delivered. All three dashboards rendered with that data.
- In the demo the diagnosis is marked low confidence. The gateway has only just started, so the hour of history it compares against is mostly empty and the size of the change is overstated. With real history it compares against normal traffic.
- Not checked: the dashboards in other Grafana versions, more than one gateway instance behind the compose stack, and the metrics under real load.

## Revisit when

- Showcasing frontend skills is a goal, or customer-facing per-tenant views with row-level access are needed.
